# 설정 값 확장 — 등록 항목 2건 (열림 2 · 닫힘 0)

출처는 #53 이다 — CLI 설정 파일의 `${VAR}` 를 손으로 나열한 다섯 자리에서만 풀던 것을 **모든 스칼라와
모든 매핑 키**로 넓힌 작업. 설계는
[`../design/integration/config-value-expansion-and-frontmatter-strictness.md`](../design/integration/config-value-expansion-and-frontmatter-strictness.md)
이고, 그 문서 §9 의 미해결 항목과 §4.1 의 결정 하나 중 **이 국면 밖으로 결과가 나가는 것**이 여기로
올라왔다.

나머지는 설계 문서에 그대로 남는다 — OQ-2(비-`String` 키에 `${VAR}` 가 닿는 것)와 OQ-3(#74 의 사정거리)은
이 작업 안에서 리뷰가 답했고, OQ-4(`cli.prompt` 도 풀린다) · OQ-5(`mcp.servers[].env` 의 **키**도 풀린다) ·
OQ-6(설계 문서 정정) · OQ-7(형제 런과의 문서 충돌면)은 이 국면 안에서 끝났다. #74 쪽에서는 열린 항목이
나오지 않았다 — 그 이슈가 답을 요구한 것 하나(*"파서의 다른 곳에도 같은 관대함이 있는가"*)는 파일 308줄
전수 조사로 답했고, 찾은 것은 전부 고쳤다.

`README.md` 의 규칙대로 **열림/닫힘의 정본은 이 문서**이고 설계 문서 §9 는 설계 시점의 기록이다.

줄 번호는 **마지막 확인 날짜와 함께** 적는다. 아래 인용은 전부 2026-09-10 기준이다.

## CE-1 — 리터럴 `${` 를 적을 방법이 없다 · **열림**

**무엇을.** `$${VAR}` → 리터럴 `${VAR}` 같은 escape 를 둘 것인지 정한다. 두기로 하면
`PlaceholderExpandingParser.expand` 한 곳의 두 줄이다.

**왜.** 규칙이 "모든 스칼라와 모든 매핑 키" 가 된 순간, 값 안에 리터럴 `${FOO}` 를 쓰는 방법이
**사라졌다**. 변수가 설정되어 있으면 조용히 치환되고, 설정되어 있지 않으면 부팅이 실패한다 — 어느 쪽도
"그대로 두라" 를 표현하지 못한다. 관측 가능한 결과는 후자다: **자식 프로세스에게 넘길 셸 플레이스홀더를
적은 배포가 기동하지 못한다.**

그럴듯한 피해자는 오늘 정확히 하나다 — `mcp.servers[].args`. stdio MCP 서버의 인자는 우리가 아니라
**자식 셸이 풀어야 하는** `${…}` 를 담을 수 있고, 이 작업 전에는 그 배열이 확장 대상이 아니었다
(`resolveMcpServerEnvVars` 가 훑던 것은 `command` · `url` · `env` 값 셋뿐이다). 같은 엔트리의
`command` 는 그때도 풀렸으므로, **이 항목이 새로 여는 것은 `args` 하나**다.

**어디.** `PlaceholderExpandingParser.expand`(2026-09-10) — `ENV_VAR_PATTERN` 이 값 하나를 훑는 유일한
자리. 설계의 기각 근거는 같은 문서 §2.3 A6.

**심각도는 세지 않았다.** in-tree 에 `${` 를 리터럴로 원하는 값은 없고(`default-config.yaml` 의 두
`${…}` 는 주석 안 예시이며 둘 다 실제 환경 변수를 뜻한다), 이 항목을 등록하는 근거는 재현이 아니라
**표현 불가능성**이다. 즉 규칙 셋이 요구하는 "돌려 본 심각도" 가 아직 없다 — 그 숫자는 첫 피해자가
가져온다.

**언제 다시 볼까.** 셋 중 하나다.

1. `mcp.servers[].args` 나 다른 값에 리터럴 `${` 가 필요하다는 보고가 들어올 때. 그때 이 항목은
   결정이 아니라 두 줄짜리 착수다.
2. MCP stdio 서버 설정을 넓히는 작업이 이 자리를 지날 때.
3. 두 번째 escape 후보(예: `\\${`)가 다른 이유로 논의될 때 — escape 를 **하나** 고르는 자리이므로
   두 논의가 따로 굴러가면 안 된다.

## CE-2 — 같은 키를 두 번 적으면 여전히 조용히 뒤엣것이 이긴다 · **열림**

**무엇을.** yaml 매핑 안에 **문자 그대로 같은 키**가 두 번 적힌 것을 보고할지 정한다. 지금은 보고하지
않는다.

**왜.** 이 작업이 없애려던 결함의 정의는 *"작성자가 적은 값이 말없이 버려진다"* 인데, 그 정확한 모양이
한 자리에 남아 있다. `modelCapabilities: { prod-assistant: {...}, prod-assistant: {...} }` 는 Jackson
이 last-wins 로 받아들이고(**실측: `OK`**, 2026-09-10) 앞엣것은 사라지며 아무도 말하지 않는다.

새로운 것은 결함이 아니라 **볼 수 있게 되었다는 사실**이다. 예전 가드는 바인딩이 끝난 뒤
`Map<String, ModelCapabilityConfig>` 를 훑었으므로 리터럴 중복은 그 지점에 닿기 전에 이미 뭉개져
있었다 — 구조적으로 볼 수 없었다. 새 가드는 토큰 스트림 위에 있고 **두 `FIELD_NAME` 을 모두 본다.**
그런데도 통과시키기로 한 것은 결정이다: 확장이 만든 충돌만 거절하고(`prod` 옆의 `${P}` → `prod` 는
오늘도 거절되고 앞으로도 거절된다), 확장과 무관한 중복은 다른 계층의 다른 결함이므로 **어느 이슈도
요구하지 않은 기동 실패를 새로 만들지 않는다**. 근거는 설계 §4.1 의 충돌 항목.

**어디.** `PlaceholderExpandingParser.Level.recordSibling`(2026-09-10) — 두 written 철자가 확장 결과와
모두 같으면 통과시키는 한 줄. 처분을 뒤집는다면 그 조건 하나와 메시지 하나다(리터럴 중복에는 "both
expand to" 가 거짓말이 되므로 문구가 따로 필요하다).

**처분을 뒤집는 것이 이 자리에서만 끝나지 않는다는 것도 함께 적는다.** snakeyaml 은 같은 질문에 대해
`LoaderOptions.allowDuplicateKeys` 라는 자기 노브를 갖고 있고, `MarkdownAgentDefinitionParser` 의
javadoc 은 그 옵션을 기본값에서 **건드리지 말라**고 명시한다(*"tightening one (duplicate keys, nesting
depth, code-point limit) would change what this repository's existing agent definitions parse to"*).
즉 이 저장소에는 이미 "중복 키를 조이지 않는다" 는 결정이 다른 표면에 하나 있다. 두 표면이 서로 다른
답을 하게 할 것인지가 실제 질문이며, 그것이 이 항목이 착수가 아니라 **결정** 항목인 이유다(규칙 넷).

**언제 다시 볼까.** 둘 중 하나다.

1. 중복 키로 값을 잃은 배포가 보고될 때.
2. 에이전트 프론트매터 쪽에서 `allowDuplicateKeys` 를 다시 여는 논의가 생길 때 — 두 표면의 답은 같은
   커밋에서 정해져야 한다.
