# 쉬는 세션 깨우기 (Idle Wake)

> Status: **IMPLEMENTED** — §10 의 1단계(라우터를 쓰는 스택). CLI 는 2단계다. 구현이 설계에서 벗어난 점은 §12.
>
> 적용 대상: `aimon-session-routing` — `at.aimon.session.routing.wake` (`IdleSessionWaker`, `WakePolicy`,
> `WakeLedger`, `InMemoryWakeLedger`) · `aimon-bootstrap` — `SessionSpec` 설정과 조립 · `aimon-spring-boot-starter`
> — `aimon.session.wake.*`. 선행 설계: [`../tool/monitor.md`](../tool/monitor.md) §9.1 (이 기능을 미룬 이유),
> [`routing.md`](routing.md) (제출·턴 게이트·인박스·이벤트 릴레이).

---

## 1. 문제

백그라운드 모니터(`Monitor`)의 알림과 백그라운드 서브에이전트의 완료 알림은 세션을 지정한 큐 항목으로 들어가고,
**다음 턴**이 그것을 읽는다(모니터 설계 §6.2). 진행 중인 턴이라면 곧바로, 쉬는 세션이라면 사용자가 다시 입력할
때까지 기다린다. 사용자가 "배포 로그를 지켜보다가 에러가 나면 원인을 찾아 줘" 라고 맡기고 자리를 비우면, 에러가
나도 아무 일도 일어나지 않는다. 모니터의 가치 절반이 여기 있다.

필요한 것: **세션이 쉬고 있을 때 그 세션을 지정한 알림이 도착하면, 그 알림을 입력으로 턴을 하나 연다.**

**하지 않는 것**:
- 기본으로 켜지 않는다. 사용자 입력 없이 LLM 호출이 생기는 첫 경로다 (§4)
- 노드 사이로 큐를 옮기지 않는다. 깨우는 노드는 알림이 들어온 노드다 (§7)
- CLI 는 1단계에 없다 (§8)

## 3. 구조

```
 MonitorManager / 서브에이전트 ──enqueue──▶ MessageQueueManager ──ENQUEUED──▶ IdleSessionWaker.onQueueEvent
                                                                              │ (생산자 스레드: 일정만 잡는다)
                                                                              ▼
                                                     디바운스 2초 뒤, 깨우기 스레드에서:
                                                       1. 레코드·바인딩·소유자 확인 (없으면 그만)
                                                       2. 상한 확인 (넘었으면 그만 — 알림은 큐에 남는다)
                                                       3. 이 노드가 쥔 세션이 진행 중이면 그만
                                                       4. drainForInjection(그 세션·runtime·kind 의 항목)
                                                       5. SessionRouter.submit(알림, principal=소유자)
                                                          동기 실패 → 꺼낸 항목을 큐에 되돌림
                                                       6. future 완료 시 연속 횟수 갱신 (기다리지 않는다)
```

### 3.1 왜 라우터인가, 어느 스레드인가

턴을 여는 데 필요한 것은 전부 라우터에 있다. 세션 레코드를 읽어 바인딩된 agent 를 확인하고, 라이브 세션이 축출되어
있으면 다시 열고, 세션당 턴 게이트로 직렬화하고, 다른 노드가 쥔 세션이면 인박스로 전달하고, 턴의 이벤트를 구독자에게
릴레이한다. 깨우기가 이것을 다시 만들면 라우터와 어긋나는 두 번째 턴 경로가 생긴다. 그래서 깨우기는 **라우터의
클라이언트**다 — 사용자의 HTTP 요청 대신 큐 이벤트가 `submit` 을 부르는 것뿐이다.

큐 리스너는 큐에 넣은 쪽의 스레드(모니터 source, 턴 스레드, `offerAsync`)에서 동기로 불린다. `submit` 은 턴을
기다리지 않지만 반환 전에 저장소·시그널 버스 I/O 를 한다. 그래서 리스너는 세션별 디바운스 일정만 잡고 돌아오고,
1–6 은 깨우기 자신의 단일 스케줄러 스레드에서 한다. 제출한 턴의 future 는 기다리지 않고 완료 콜백만 단다.

### 3.2 깨우는 턴의 입력

`submit` 은 사용자 입력 하나를 요구한다. 자리표시 입력("이벤트가 왔다")을 보내고 알림은 턴 시작 드레인(모니터 설계
§6.2)에 맡기는 방법은 택하지 않는다. 턴 시작 드레인은 큐가 노드 로컬이라 그 턴이 같은 노드에서 돌 때만 동작한다 —
세션이 다른 노드에 있어 제출이 인박스로 전달되면 알림은 이 노드의 큐에 남는다.

그래서 깨우는 쪽이 **그 세션의 깨울 항목을 직접 드레인**하고, 각 항목 본문을 `SystemReminderFormatter.sanitizeBody`
로 다듬은 뒤 `wrap("background-wake", …)` 로 감싸 이어 붙여 턴의 입력으로 보낸다. 입력이 곧 알림이므로 어느 노드에서
돌든 전달된다. 드레인은 `DRAINED` 이벤트를 내므로 모니터는 다음 묶음을 큐에 넣고, "모니터당 대기 항목 하나"
불변식도 그대로다. 드레인 필터는 실행기와 같다 — runtime 과 세션이 모두 맞는 항목만.

**대가**: 감싼 입력도 전사에는 사용자 역할의 메시지로 남는다(메모리 수집에서도 그렇게 보인다). 턴 도중 주입되는 큐
항목이 같은 감싸기를 쓰므로 일관되지만, 자리표시 입력보다 낫다는 근거는 위의 노드 문제이지 전사의 깨끗함이 아니다.

턴에는 실행 속성 `aimon.wake.reason` (깨운 항목의 kind 를 쉼표로 이은 문자열 — 실행 속성 값은 문자열이어야 한다)을
붙여 TURN 스팬에서 깨운 턴을 구별할 수 있게 한다. 서브에이전트 완료 알림으로 깨웠으면 CLI 재생과 같이
`SubagentTaskCompleted.RECEIVED_TASK_ID_ATTRIBUTE` 도 붙인다(여러 개면 첫 것). 제출에는 **시도마다 새** 멱등 키
`wake:<첫 항목 uuid>:<무작위>` 를 준다 — 인박스로 전달된 제출의 future 를 정리하는 데 라우터가 그 키를 쓰고, 전달에
실패한 키는 몇 분 동안 진행 중으로 남으므로 같은 항목을 되돌려 다시 보낼 때 같은 키를 쓰면 라우터가 중복으로 삼킨다.

**재오픈 옵션.** 라우터는 축출된 세션을 다시 열 때만 `LiveSessionOptions` 와 `OpenAttributes` 를 적용하고, 그 값은
다음 축출까지 이어진다. 깨우는 턴이 기본값으로 세션을 열면 이후의 사용자 턴도 그 기본값으로 돈다. 그래서 호스트가
자기 제출에 싣는 값을 채우는 `WakeRequestCustomizer` 를 둔다(`SessionSpec.wakeRequestCustomizer`, Spring 빈). 드레인
전에 불리고, 던지면 깨우지 않는다.

`agentRef` 는 세션 레코드의 바인딩에서 읽고(바인딩이 없는 세션은 깨우지 않는다), discriminator 는 항목의
`AgentRuntimeId.discriminator()` 에서 읽는다.

### 3.3 언제 깨우지 않는가

- **레코드가 없거나, 바인딩이 없거나, 소유자가 없으면.** 제출 직전에 다시 읽는다 — 다른 노드에서 세션이 삭제된 뒤
  디바운스가 끝나도, 제출이 레코드를 되살리지 않게
- **상한을 넘었으면**(§4.3). 알림은 큐에 남아 다음 사용자 턴이 읽는다. 버리지 않는다
- **이 노드가 쥔 세션이 진행 중이면** — `SessionRouter.status(id)` 의 phase 가 `RUNNING` 이거나 `isInterruptible()`
  (OnStart 훅 구간까지 덮는다). 이것은 **비용 최적화**다. 라우터의 javadoc 대로 status 는 제어 게이트가 아니고,
  슬래시 명령 턴이나 턴 사이의 짧은 구간에서는 IDLE 로 읽힌다. 그 틈에 제출하면 라우터는 턴을 겹치지 않고 지금
  턴 **뒤의 별도 턴**으로 줄 세운다 — 알림은 늦어지고 LLM 턴이 하나 더 생기지만 잃지는 않는다. 다른 노드가 쥔
  세션은 status 가 UNKNOWN 이고, 그 노드의 턴은 이 노드의 큐를 읽을 수 없으므로 깨우는 것이 맞다
- **드레인한 항목이 없으면** — 그사이 다른 턴이 가져갔다

## 4. 정책

### 4.1 무엇이 깨우는가

`WakePolicy.kinds` — 깨우는 큐 항목의 `metadata.kind` 집합. 기본값은 모니터 알림(`monitor-event`) 하나다.
서브에이전트 완료 알림(`subagent-task-completed`)은 더할 수 있다. 세션을 지정하지 않은 항목과 사용자 후속
입력(kind 없음)은 깨우지 않는다 — 후속 입력은 그 자체가 사용자의 턴이 이미 돌고 있다는 뜻이다.

모니터 알림만 기본으로 둔 이유: 모델이 모니터를 건 것은 "이 이벤트에 반응하라" 는 뜻이지만, 백그라운드 서브에이전트는
결과를 나중에 읽으려고 띄운 경우가 많다. 완료마다 턴을 여는 것은 배포가 고를 일이다.

### 4.2 누구로, 무엇에 잡히는가

깨우는 턴의 `SubmitOptions.principal` 은 **세션 소유자**(`SessionRecordStore.loadOwner`)다. 이 principal 이 요청
principal 이 되어 사용량 쿼터·실행 환경·도구 컨텍스트로 간다. `SubmitRequest.initiator` 는 `Principal.system()` —
제출한 것은 사람이 아니라 프레임워크다.

**소유자가 없는 세션은 깨우지 않는다** — 비용을 누구에게 매길지 모르는 턴은 열지 않는다. 소유자는 그 세션의 첫
제출이 `SubmitRequest.owner` 를 줬을 때만 기록된다. 소유자를 기록하지 않는 호스트에서는 깨우기가 아무 일도 하지
않으므로, 깨우기는 소유자 없는 세션을 처음 만날 때 그 사실을 세션마다 한 번 WARN 으로 남긴다.

예산(`ExecutionBudget`), 사용량 쿼터, `SessionTotals` 는 따로 다루지 않는다. 라우터를 거친 턴이므로 일반 턴과
똑같이 잡힌다.

### 4.3 폭주 방지

깨운 턴이 다시 모니터를 걸고, 그 모니터가 다시 깨우는 고리가 가능하다. 세 겹으로 막는다.

| 장치 | 기본값 | 무엇을 막나 |
|------|-------|-----------|
| 디바운스 | 2초 | 한 사건의 알림 여러 개가 턴 여러 개가 되는 것 — 창 안의 항목을 한 턴으로 모은다 |
| 세션당 시간당 깨우기 | 6회 | 시끄러운 모니터가 비용을 태우는 것 |
| 사용자 턴 없는 연속 깨우기 | 3회 | 깨움 → 모니터 → 깨움 의 고리. 사용자 턴이 한 번 돌면 0 으로 돌아간다 |

**사용자 턴을 어떻게 아는가.** 스트림 이벤트에는 턴 id 도 실행 속성도 없고, 슬래시 명령 턴이나 라우터 안에서 실패한
턴은 `ExecutionCompleted` 를 내지 않으며, 느린 구독자의 이벤트는 버려진다. 그래서 이벤트로는 세지 않는다. 대신
영속된 **`SessionTotals.turnCount`** 를 쓴다(ReAct 루프에 들어간 턴마다 하나씩 는다).

- 깨운 턴의 future 가 끝나면 그 시점의 `turnCount` 를 레코드에서 읽어 원장에 적는다
- 다음에 깨우기 전에 다시 읽은 `turnCount` 가 적어 둔 값보다 크면, 그사이 **다른 턴**이 돈 것이다 → 연속 횟수 0
- 원장에 적힌 값이 없거나(첫 깨우기) 저장소가 합계를 영속하지 않으면(늘 0) 초기화 근거가 없으므로 연속 횟수는 그대로
  센다 — 상한 쪽으로 틀린다

상한에 걸린 세션은 다음 사용자 턴까지 깨우지 않고, 그 사실을 세션마다 한 번 INFO 로 남긴다.

**깨운 턴이 진행 중일 때.** 깨운 턴 자신도 `turnCount` 를 늘리므로, 그 턴이 끝나 기록하기 전에 다음 깨우기를 판단하면
제 턴을 사용자 턴으로 착각해 연속 횟수를 지운다. 원장의 `outstanding` 표시가 그 구간을 덮는다 — 깨운 턴을 제출할 때
세우고 그 턴이 끝나 `turnCount` 를 기록할 때 내리며, 세워져 있는 동안은 초기화하지 않는다.

**시간당 상한이 풀릴 때.** 대기 항목이 있는 모니터는 새 항목을 넣지 않으므로 새 이벤트도 오지 않는다. 그래서 시간당
상한에 걸리면 가장 오래된 깨우기가 한 시간 창을 벗어나는 시각에 다시 확인을 예약한다.

**`WakeLedger`.** 세션별 카운터(시간당 깨우기 시각들, 연속 횟수, 마지막으로 본 `turnCount`, `outstanding`)는 멀티
인스턴스 규칙에 따라 SPI 뒤에 두고, 변경은 원자적 `update(id, 함수)` 로만 한다 — 깨우기와 턴 종료가 같은 세션의 상태를
바꾸고, 공유 구현에서는 다른 노드도 바꾸므로 읽고 쓰기를 나누면 셈을 잃는다. 기본은 `InMemoryWakeLedger` 다. 이
노드 안에서는 턴 종료 처리도 깨우기 스레드로 옮겨 한 스레드가 바꾼다. 공유 구현을 주면 노드 사이에서 상한을 공유할 수 있다(§11 W-2).
디바운스 타이머는 노드 로컬로 남는다.

## 5. 실패

드레인한 뒤에 제출이 실패하면 꺼낸 알림은 큐로 돌아가야 한다 — 모니터는 드레인된 묶음을 다시 보내지 않는다.

| 실패 | 처리 |
|------|------|
| 검증 실패 (레코드·바인딩·소유자) | 드레인하기 **전**에 확인하므로 꺼낸 것이 없다 |
| `submit` 이 동기로 던짐 (`ConflictingAgentException`, 라우터 종료, 인박스 쓰기 실패) | 꺼낸 항목을 같은 uuid·메타데이터로 큐에 되돌린다. 되돌린 직후의 `ENQUEUED` 가 곧바로 다시 깨우지 않도록 그 세션은 30초 뒤로 미룬다 |
| 인박스로 전달된 제출의 future 가 **확실히 실행되지 않은 채** 실패 (인박스 쓰기 실패, 대기 중 세션 해제·삭제·EVICT — 인박스가 함께 비워진다) | 라우터가 `ForwardNotRunException` 으로 알린다. 깨우기는 future 가 끝날 때까지 꺼낸 항목을 들고 있다가 큐에 되돌리고, 그 깨우기를 상한 셈에서 빼고, `retryDelay` 뒤 다시 시도한다 |
| 인박스로 전달된 제출의 future 가 **실행 여부를 모른 채** 실패 (전달 TTL 경과, 예약 유실, 라우터 종료) | 되돌리지 않는다. 그 턴은 다른 노드에서 돌았을 수 있고, 같은 알림으로 턴이 두 번 도는 것이 한 번 잃는 것보다 나쁘다. WARN 으로 남긴다 |
| 턴이 돌다 실패 (오류·쿼터) | 일반 턴과 같다. 알림은 입력으로 전사에 남았다 |

---

## 6. 수명

`IdleSessionWaker` 는 **Application** 수명이다(라우터와 같다). 스택은 라우터를 만든 뒤 깨우기를 만들고 큐 리스너를
건다. teardown 은 `TeardownPhase.SESSIONS` 안에서 라우터 **다음에 등록**한다 — 같은 단계는 등록의 역순으로 닫히므로
깨우기가 라우터보다 먼저 닫힌다. 닫을 때 큐 리스너를 떼고, 디바운스 일정을 취소하고, 스케줄러를 멈춘다.

세션이 삭제되면 그 세션의 디바운스 일정과 원장 항목을 지운다. 라우터의 수명 리스너는 라우터를 만들기 전에 넘겨야
하므로, 스택은 모니터 매니저처럼 늦게 바인딩되는 어댑터를 라우터에 걸고 깨우기를 만든 뒤 연결한다. 삭제 이벤트는 삭제한
노드에서만 오므로, 다른 노드의 일정은 제출 직전 레코드 재확인(§3.3)이 막는다.

---

## 7. 여러 노드

큐는 기본적으로 노드 로컬이므로, 알림은 그것을 낸 노드(모니터가 도는 노드)의 큐에만 있고 그 노드의 깨우기만 반응한다.
그 노드가 세션을 쥐고 있지 않으면 `submit` 은 인박스로 전달되고, 세션을 쥔 노드가 그 입력으로 턴을 연다. 입력이 곧
알림이므로(§3.2) 이것으로 충분하다. 기본 `InMemoryWakeLedger` 로는 상한을 노드마다 따로 센다 — 1단계에서 받아들이는
근사이고, 공유 원장이 그 답이다.

## 8. CLI — 2단계

CLI 는 라우터가 아니라 `LiveSession` 을 직접 쓰고, REPL 스레드가 JLine 입력에서 기다린다. 쉬는 동안 턴을 열면 그
출력이 입력 줄 위로 끼어든다(`LineReader.printAbove` 로 다시 그려야 한다). 이 UX 문제는 깨우기의 정책과 무관하므로
1단계에서 뺀다.

## 9. 기각한 것

### 9.1 모니터 안에서 깨우기

`MonitorManager` 가 직접 턴을 열면 서브에이전트 알림은 혜택을 못 받고, 모니터가 라우터·세션 레코드·principal 을
알아야 한다. 도구 계층이 세션 계층에 의존하게 된다.

### 9.2 `LiveSession` 에 큐 리스너 달기

라이브 세션은 축출되면 없어지므로 쉬는 세션 — 바로 깨워야 할 대상 — 일수록 리스너가 없을 가능성이 크다. 그리고
라우터를 거치지 않으면 이벤트 릴레이와 노드 간 직렬화를 잃는다.

### 9.3 자리표시 입력 + 턴 시작 드레인

## 12. 구현이 설계에서 벗어난 점

| 항목 | 설계 | 구현 | 이유 |
|------|------|------|------|
| 진행 중인 세션 | 깨우지 않고 그만 (§3.3) | 깨우지 않되 디바운스 간격 뒤 **다시 확인**한다 | 진행 중인 턴이 도구 iteration 없이 답하고 끝나면 알림이 다음 사용자 턴까지 남는다. 새 알림이 오지 않으면 아무도 다시 보지 않으므로, 턴이 끝날 때까지 짧게 다시 본다 |
| 전달 실패 시 되살리기 (옛 W-3) | 되돌리지 않는다 | 확실히 실행되지 않은 경우(`ForwardNotRunException`)만 되돌리고, 실행 여부를 모르는 경우는 그대로 (§5) | 라우터가 그 둘을 구별해 알려 줄 수 있었다 — 인박스 쓰기 실패와 인박스를 비우는 해제·삭제·EVICT 는 확실히 실행되지 않은 경우다 |
| PR 리뷰 반영 | 멱등 키 `wake:<uuid>`, `get`/`put` 원장, 진행 중이면 레코드부터 읽고 재확인, 재오픈 옵션 없음 | 시도마다 새 키(§3.2), 원자적 `update` 와 `outstanding`(§4.3), 진행 중 확인을 먼저 하고 남은 항목이 있을 때만 재확인, `WakeRequestCustomizer`(§3.2), 시간당 상한이 풀릴 때 재확인, close 는 진행 중인 깨우기를 기다린다 | 재시도가 중복으로 삼켜지는 유실, 원장 경합과 제 턴에 의한 초기화, 불필요한 저장소 읽기, 기본값으로 열린 세션 |
| 설계 리뷰 반영 | 첫 초안은 드레인 뒤 검증, `status` 를 게이트로, 이벤트로 자기 턴 세기 | 드레인 전 검증 + 실패 시 되돌리기(§5), `status` 는 이 노드가 쥔 세션의 비용 최적화(§3.3), `turnCount` 로 사용자 턴 판정(§4.3) | 리뷰가 찾은 유실·경합·카운터 어긋남 |
