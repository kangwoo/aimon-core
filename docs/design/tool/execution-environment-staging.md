# 실행 환경 스테이징 — 제어 저장소의 파일을 작업 환경으로 옮긴다

> **Status**: IMPLEMENTED — `aimon-core` 의 `ExecutionEnvironment.stage` 계약, `StagedResource`, 로컬 구현 `LocalStaging`, 스킬 저장소의 `resolveSource`. 남은 것은 [§17](#17-남은-것).

## 1. 왜 스테이징하는가

스킬 정의(`SKILL.md`)는 프레임워크가 제어 저장소에서 JVM 으로 직접 읽으므로 환경과 무관하다. 스테이징이 필요한 것은
모델이 스킬 본문을 따라 **스킬 디렉터리 안의 다른 파일**(스크립트, 참고 문서)을 셸이나 파일 도구로 열 때다. 제어 저장소
경로를 `${AIMON_SKILL_DIR}` 로 주면 셸과 파일 시스템이 우연히 같은 디스크일 때만 동작한다. 그래서 `stage()` 가 파일
집합을 환경 안에 복사하고, 그 환경의 셸과 파일 도구가 함께 쓸 수 있는 절대 경로를 돌려준다.

내용 주소, 매 호출 검증, 소스와 렌더 규칙(§3, §4, §9~§12)은 `stage()` 를 쓰는 쪽의 계약이고 복사 방식, 스윕, 입력 검증
(§5, §6, §13, §14)은 로컬 제공자의 구현이다. 제공자가 지킬 항목의 표는 [실행 환경](execution-environment.md) 의 샌드박스
제공자 계약 절에 있고, 제어 저장소와 작업 환경의 경계는 [파일 규칙](execution-environment-files.md) 에 있다.

## 2. 설계 결정

| 쟁점 | 결정 | 이유 | 기각한 대안 |
|---|---|---|---|
| 사본의 이름 | `{stagingRoot}/{name}/{contentKey}/` | 원본이 바뀌면 경로가 바뀌므로 옛 사본을 덮어쓰거나 지울 일이 없고, 먼저 렌더된 본문의 경로가 계속 유효하다 | 호출마다 소스 해시: 스킬 디렉터리 전체를 매번 제어 저장소에서 읽는다 |
| 사본을 믿는 근거 | 호출마다 마커·파일 집합·해시를 내용 키에 대조한다 | 같은 uid 의 셸이 호출 사이에 사본을 고칠 수 있다 | 제공자 메모리의 "이미 올렸다": 비영속 환경은 재생성되면 사본이 사라지는데 기록은 남는다. 마커만 신뢰: 키는 예측 가능하므로 저장소에 커밋되거나 셸로 심은 사본도 경로와 마커를 함께 갖는다. 앞선 검증을 기억: 그 사이의 변조를 놓친다 |
| 복사 대상 | 형제 임시 디렉터리에 쓰고 검증한 뒤 이름을 준다 | 제공자의 잠금은 JVM 안에서만 유효하다. 다른 프로세스가 같은 대상을 복사하거나 그 스크립트를 돌리고 있을 수 있다 | 대상에 직접 복사 |
| 접은 이름이 겹치는 자원 | 합쳐진 사본만 거부한다 | 겹친다는 것은 합쳐질 수 있다는 뜻일 뿐이다. 대소문자를 구분하는 디스크에서는 정상으로 스테이징된다 | 겹치면 무조건 거부 |
| 적재 뒤 바뀐 소스 | 다시 스캔해 지금 내용의 키로 스테이징한다 | 지키는 불변식은 하나다. 바이트를 그것이 해시되지 않는 키 아래 두지 않는다 | 거부: 재시작 말고 길이 없는 오류가 된다 |
| 조립된 자원의 재스캔 | 하지 않는다. 기록대로 스테이징하거나 거부한다 | 손수 조립한 자원의 디렉터리에는 일부러 뺀 파일이 있을 수 있다. 다시 스캔하면 그 파일이 모델에게 보인다 | 모든 자원을 재스캔 |
| 소스가 없는 저장소 | 모든 스킬 저장소가 `resolveSource` 를 구현한다 | 스킬이 어디서 왔든 `${AIMON_SKILL_DIR}` 는 `stage()` 의 반환값 하나다 | 호스트 경로 스킬의 경로를 그대로 쓰기: 비로컬 제공자에는 그 경로가 없다 |
| 호스트 경로 소스의 구현 | 별도의 `ReadOnlyLocalFileSystem` | 읽기 전용이거나 없는 스킬 디렉터리에서도 동작해야 한다 | `LocalFileSystem` 위의 읽기 전용 래퍼: `initialize()` 가 없는 루트를 만들고 쓸 수 없는 루트를 거부하며, 읽기마다 초기화를 확인한다 |
| `.stageignore` 해석기의 자리 | `at.aimon.core.environment.StageIgnore` | 해시와 복사가 같은 파일 집합을 보아야 하고, 의존 방향은 `skill → environment` 뿐이어야 한다 | `skill` 패키지의 클래스 |
| 범위 밖 링크 | 소스 스캔을 거부해 그 스킬을 적재하지 않는다 | 조용히 빠진 파일로 만든 사본이 `${AIMON_SKILL_DIR}` 에 놓이는 것보다 적재 실패가 낫다 | 건너뛰기: 빈 사본이 놓인다 |
| 적재 실패의 범위 | 그 스킬 하나 | 목록이 `Skill` 도구 정의, `/skills`, 스킬 기반 슬래시 커맨드, REPL 배너의 재료다. 하나의 실패가 전부를 무너뜨리면 안 된다 | 목록 전체 실패 |
| 머티리얼라이저 | `BundledSkillMaterializer` 를 유지한다([EE-6](../../backlog/execution-environment-open-items.md)) | 비용은 스킬 한 버전당 복사 한 번이다. 없애면 부트스트랩 층 구성, `StackPaths`, `AimonRuntimeHints`, 문서화된 디렉터리 배치가 함께 움직인다 | 클래스패스 저장소가 직접 스테이징하게 하고 은퇴 |
| 격리 브랜치의 사본 | 부모와 같은 스테이징 영역을 쓰고, 언제나 사본을 준다 | 스테이징 영역은 브랜치의 파일 도구와 셸이 같은 파일을 보는 유일한 자리다 | 브랜치마다 복사. 브랜치에 제자리 경로 주기 |
| 포크 본문의 렌더 | 포크의 환경이 부모와 다르고 본문이 변수를 쓸 때만 다시 렌더한다 | 쓰지 않는 본문은 어디서나 같고, 재렌더는 아무도 읽지 않는 사본을 만들며, 스테이징할 수 없는 환경에서 멀쩡한 포크를 훅 전에 끝낸다 | 모든 포크 재렌더. 렌더된 본문에서 경로 문자열 치환: 같은 경로가 인자나 글에 나올 수 있다. 포크 모드에서 호출 쪽 스테이징 생략: `subagentStart` 의 goal 과 스팬 입력에 글이 필요하다 |
| 스윕의 범위 | 소유 모드에서, 시작할 때, 유예가 지난 것만 | 공유 VFS 는 다른 런타임이 쓰는 중일 수 있다. 유예는 실행이 띄운 프로세스가 살아 있을 수 있는 시간과 맞춘다 | 빌린 VFS 도 스윕 |
| 스윕과 링크 | 따라가지 않는다 | 지우는 쪽이고, 스테이징 디렉터리는 저장소 커밋이나 셸이 링크로 바꿀 수 있다 | 링크를 따라가며 지우기 |

## 3. 내용 주소

사본은 `{stagingRoot}/{name}/{contentKey}/` 에 놓인다. 로컬의 스테이징 루트는 작업 트리 아래 디렉터리 이름 하나이고
기본값은 `.aimon-staged` 다. `stage()` 의 반환값은 이 사본의 절대 경로이므로 셸의 현재 디렉터리와 상관없이 풀린다.
호스트 디렉터리가 워크스페이스면 `{workspace}/.aimon-staged/{name}/{key}` 이고, URI 모양의 백엔드에서는
`/.aimon-staged/…` 처럼 그 백엔드가 받는 표기다.

파일 집합의 규칙은 `StagedResource.scan` 한 곳에 있다. 소스 디렉터리를 재귀로 나열하고 `.stageignore` 가 뺀 경로를 버린 뒤
나머지를 읽어 `getFiles()` 에 기록한다. `stage()` 는 정확히 `getFiles()` 만 복사한다. 내용 키는 경로순으로 정렬한
`relPath + '\0' + bytes + '\0'` 항목들의 SHA-256 앞 16자리 소문자 16진수다. 끝의 구분자는 두 항목이 이어 붙어 같은 입력이
되는 일을 막는다.

키와 관련된 읽기는 세 가지로 나뉜다.

- **소스의 키는 적재 때 계산한다.** 레지스트리가 정의를 읽거나 다시 읽을 때 한 번 해시해 `StagedResource` 에 싣는다.
- **사본은 호출마다 키에 대조한다.** §4 의 검증이다.
- **소스는 바뀐 판을 기억 중일 때만 호출마다 읽는다.** §7 의 경우다.

복사의 마지막에 `.staged` 마커를 쓴다. 첫 복사는 스테이징 루트에 `*` 한 줄짜리 `.gitignore` 도 쓰므로 사본이 버전 관리에
들어가지 않고 프로젝트 초기화 단계가 필요 없다. 옛 키의 사본은 실행 중에 지우지 않는다. 아직 그 경로를 들고 있는 실행이
있을 수 있기 때문이다. 정리는 §13 의 몫이고, 비영속 환경에서는 재생성되면 사본도 함께 사라진다.

## 4. 매 호출 검증

`stage()` 의 계약은 다음과 같다. **기존 사본은 호출마다 마커, 파일 집합, 해시를 내용 키에 대조하고, 다르면 다시 복사한다.**
앞선 호출이 확인했다는 이유로 사본을 내주지 않는다. 생략 여부는 대상 환경에 있는 사본을 보고 판단한다. 비영속 환경이
재생성되면 마커가 없으므로 다시 복사하고, 끊긴 복사에도 마커가 없으므로 다음 호출이 다시 한다.

파일 도구에는 스테이징 영역이 읽기 전용이지만 셸은 쓸 수 있다. 셸은 호출 사이에 사본을 고칠 수 있지만 다음 `stage()` 가
되돌린다. 원본은 영향받지 않는다.

- 자원의 파일이 아닌 항목은 지운다. 실행이 남긴 `__pycache__` 가 사본 전체의 재복사를 부르지 않게 하기 위해서다.
- 어긋난 사본은 옆으로 옮긴 뒤 교체하고 WARN 을 남긴다.
- 비용은 호출당 사본의 목록 하나와 해시 하나이며 스테이징 상한이 그 크기를 묶는다.
- `LocalStaging` 은 호출마다 자원별 소스 잠금과 대상 잠금을 모두 잡는다. 한 자원의 동시 호출은 검증하는 동안 줄을 서고,
  다른 자원의 호출은 서로 기다리지 않는다.

그래도 확인과 인터프리터가 경로로 다시 여는 사이의 창은 남는다. 이 검증은 경계가 아니다. 그래서 `hooks.json` 의 정책 훅은
사본이 아니라 실행 디렉터리에서 돈다. 스킬 훅은 실행 디렉터리를 쓸 수 없을 때 이 매 호출 검증 스테이징으로 물러선다.
호출자별 경로와 남는 위험은 [훅 변조 경계](../hook/hook-tamper-boundary.md) 가 소유한다.

## 5. 복사의 원자성

로컬 제공자는 파일과 마커를 형제 임시 디렉터리 `{contentKey}.tmp-{난수}` 에 쓰고 검증한 뒤에 대상의 이름을 준다. 실패한
복사는 자기 임시 디렉터리만 지우고 대상은 건드리지 않는다. 이름을 주는 방법과 보장은 워크스페이스가 할 수 있는 일에 따라
다르다.

| 워크스페이스 | 이름 주기 | 보장 |
|---|---|---|
| 호스트 디렉터리 (`workspaceRoot` 모드, 또는 작업 디렉터리가 로컬 경로인 빌린 파일 시스템) | 이름 바꾸기 한 번 | 읽는 쪽은 대상이 없거나 완전한 것만 본다. 경합에서 진 쪽은 자기 사본을 버리고 이긴 쪽의 것을 돌려준다. 유효하지 않은 대상을 교체할 때만 이름 바꾸기 두 번이고, 그 사이에 대상이 잠깐 없다 |
| 그 밖의 파일 시스템 (S3, GridFS) | 검증된 파일을 하나씩 옮기고 마커를 마지막에 옮긴다 | 원자적이지 않고 마커가 유일한 완료 표시다. 어떤 프로세스도 대상이나 그 안의 자원 파일을 지우지 않고, 검증에 실패한 바이트는 대상에 닿지 않는다. `VirtualFileSystem.move` 는 파일 하나를 옮기고 객체 저장소에서는 복사 후 삭제이므로 쓸 이름 바꾸기가 없다 |

죽은 프로세스가 남긴 임시 디렉터리는 §13 의 스윕이 지운다.

## 6. 대소문자 충돌

클래스패스, S3, GridFS 소스는 `RUN.sh` 와 `run.sh` 를 함께 가질 수 있지만 APFS 와 NTFS 는 둘에 파일 하나만 둔다. 복사 검증은
소스에서 읽은 바이트를 해시하므로 이것을 보지 못한다. 그래서 파일 이름 가운데 `VfsPaths.foldCase` 로 접어 같아지는 쌍이
있을 때에 한해, 로컬 제공자는 임시 디렉터리의 사본을 디스크에서 다시 읽어 해시한다. 키와 다르면 두 경로를 이름으로 든
`StagingException` 이다. 겹치는 쌍이 없는 자원은 다시 읽지 않는다. 접기가 예측하지 못하는 합쳐짐은
[EE-33](../../backlog/execution-environment-open-items.md) 이 소유한다.

## 7. 적재 뒤 바뀐 소스

CLI 와 부트스트랩에는 레지스트리를 다시 읽는 경로가 없다. 복사하는 바이트가 적재 때의 키로 해시되지 않거나, 기록된 파일이
없어졌거나, 파일이 상한을 넘게 자라면 로컬 제공자는 임시 사본을 버리고 소스를 **다시 스캔해** 그 결과를 자기 키 아래에
복사한다. 재시작하면 계산될 바로 그 키이므로 재시작한 프로세스가 이 사본을 재사용한다. 사본은 적재 때의 목록에 새 바이트를
채운 것이 아니라 **지금의 디렉터리**다(더해진 파일, 빠진 파일, 바뀐 `.stageignore`). 상한도 지금의 크기에 건다. 스킬 이름을
든 WARN 이 한 번 남는다.

**기억과 되돌림.** 제공자 인스턴스는 그 대응을 사본의 마커가 있고 키에 맞는 동안, 그리고 소스가 적재된 판과 다른 동안에만
기억한다. 호출마다 먼저 기록된 파일을 읽어 해시하고(아무것도 쓰지 않는다), 적재된 키로 돌아왔으면 기억을 버리고 적재된
판으로 스테이징한다. 고쳤다가 되돌린 스킬이 고친 내용으로 돌지 않게 하기 위해서다. 그 대가로 소스가 다른 동안의 호출은
사본 검증에 소스 한 번 읽기가 더해진다. 다시 스캔한 뒤 복사하는 사이에 또 바뀌면 `StagingException` 이고 다음 호출이
처음부터 다시 한다.

**이것이 바꾸는 범위.**

- 첫 복사뿐이다. 적재된 키의 사본이 이미 있으면 그 사본이 쓰이고, 그 뒤의 수정은 레지스트리가 다시 읽을 때까지 보이지 않는다.
- 파일뿐이다. `SKILL.md` 에서 읽은 본문, 도구 제한, 훅은 재적재까지 적재 판이다. 그 사이 모델은 옛 본문을 따라 새 스크립트를
  돌릴 수 있다. 스킬 디렉터리에 쓸 수 있는 사람은 어느 쪽이든 그 스크립트를 정할 수 있으므로 새 경계를 넘지 않는다.
- 스킬 훅의 실행 디렉터리 캐시도 내용 키를 키로 삼고, 항목마다 자기 바이트가 해시되는 키 아래에만 둔다. 규칙은
  [훅 변조 경계](../hook/hook-tamper-boundary.md) 에 있다.

**다시 스캔하는 것은 스캔으로 만든 자원뿐이다.** 다시 스캔해도 되는 까닭은 자원의 파일 목록이 곧 그 디렉터리이기 때문인데,
그것은 `StagedResource.scan` 이 만든 자원에만 참이다. `isScanned()` 는 `scan()` 만 참으로 만들고 빌더에는 그렇게 말할 메서드가
없다. `builder()` 로 조립한 자원은 기록된 대로 스테이징하거나 거부한다. 바이트가 키와 어긋나면 "changed on disk after it was
loaded … Restart the application, or reload the skill registry" 라는 `StagingException` 이고, 파일을 읽지 못했거나 상한을
넘었으면 그 오류다. 어느 쪽이든 목록에 없는 파일은 임시 디렉터리에도 쓰이지 않는다. 출하되는 조립에서 자원을 만드는 곳은
`DefaultSkillRegistry` 하나이고 `scan()` 을 쓴다.

## 8. 상한과 `.stageignore`

스킬 디렉터리 하나의 스테이징 총량에 상한을 둔다. 기본값 50 MiB(`DEFAULT_MAX_STAGED_BYTES`)는 artifact 파일당 상한과 같은
값이다. 넘으면 `stage()` 가 `StagingException` 을 던지고 호출자가 도구 오류로 바꾼다. 스킬 디렉터리의 `.stageignore` 로 큰
파일을 뺄 수 있고, `.stageignore` 가 전부 뺀 스킬은 작성자가 원한 것이므로 빈 사본으로 적재된다. 설정 키와 문법은
[스킬 가이드](../../features/skill/builtin-agent-skill-guide.md) 에 있다.

적재 때 이미 상한을 넘은 자원도 재시작 없이 고칠 수 있어야 한다. 오류가 "`.stageignore` 로 빼라" 고 말하기 때문이다. 그래서
기록된 크기는 마지막 판단이 아니다. 로컬 제공자는 소스의 지금 크기를 파일 메타데이터로 구한다(`StagedResource.sizeOf`, 스캔과
같은 파일 집합이고 내용은 읽지 않는다). 상한 아래로 내려왔으면 §7 처럼 다시 스캔해 그 키로 스테이징한다. 여전히 넘으면 지금의
바이트 수를 든 `StagingException` 이다.

- 그런 호출의 비용은 목록 조회 한 번과 파일당 크기 조회 한 번이다. 크기를 알려 주지 못하는 소스는 전체 스캔으로 대신한다.
- 거부는 기억하지 않는다. 사용자가 고친 직후의 호출이 그것을 본다.
- 조립된 자원은 기록된 크기가 넘으면 디렉터리를 보지 않고 거부한다.

첫 `stage()` 는 제공자의 게으른 프로비저닝을 촉발할 수 있어 첫 스킬 호출이 느릴 수 있다. 스킬을 부르지 않는 실행은 이 비용을
치르지 않는다. 적재 쪽에서는 내용 키 때문에 첫 목록이 모든 스킬의 모든 바이트를 한 번 읽는다. 큰 에셋을 가진 스킬은
`.stageignore` 로 빼지 않으면 시작이 느려진다.

## 9. 스킬 소스와 저장소 층

`SkillRepository.resolveSource(name)` 는 `stage()` 에 넘길 소스 `SkillSource` 를 돌려준다. 읽기만 하는 `VirtualFileSystem` 과 그
안의 스킬 디렉터리다. 소스는 읽기 쪽 메서드만 있으면 된다. 값이 비는 것은 스킬이 없을 때뿐이다. 스킬을 찾았는데 소스가 비면
저장소 결함으로 보고 적재가 실패한다.

| 저장소 | 소스 파일 시스템 | 스킬이 놓인 곳 |
|---|---|---|
| `VfsSkillRepository` | 자기 VFS | 제어 저장소의 `skills`, 머티리얼라이즈된 번들 스킬은 `bundled-skills` |
| `PathSkillRepository` | 저장소 루트 위의 `ReadOnlyLocalFileSystem` | 호스트 디렉터리. 번들이 `file://` 로 풀릴 때 |
| `ClasspathSkillRepository` | 트리를 걷는 읽기 전용 `ClasspathSkillSourceFileSystem` | 클래스패스 자원. 번들이 그 밖으로 풀릴 때 |

`ReadOnlyLocalFileSystem` 은 `LocalFileSystem` 위에 짓지 않는다. 만들 때 I/O 가 없고 정리할 자원도 없으므로, 읽기 전용이거나
없는 스킬 디렉터리에서도 동작한다. 클래스패스 소스는 `BundledSkillMaterializer` 와 같은 걷기를 쓴다. 클래스패스 배치를 열거할
수 없으면 소스에는 `SKILL.md` 만 보이고 경고가 남으며, 스킬은 쓸 수 있고 다른 파일에는 닿지 않는다.

**렌더.** `${AIMON_SKILL_DIR}` 에 들어가는 값은 언제나 `stage()` 의 반환값이다. `Skill` 도구, 스킬 포크, 스킬 기반 슬래시
커맨드가 모두 `SkillRenderContextAccess` 를 거친다. `skill.render` 는 환경을 모르는 채로 남는다. `StagedResource` 가 없는 손조립
`Skill` 은 빈 문자열로 렌더하고 경고하며 저장소 경로로 되돌아가지 않는다. `Skill` 도구가 모델에게 보여 주는 파일 목록도 같은
스테이징 경로 기준이고, `.stageignore` 가 뺀 파일은 목록에도 없다.

## 10. 심볼릭 링크와 읽지 못한 파일

호스트 경로 소스는 스킬 디렉터리를 훑거나 읽을 때 링크를 그 **실제 경로** 가 저장소 루트 안이거나 운영자가 명시한 허용 루트
안일 때만 따라간다. 스킬 디렉터리 자체가 링크인 경우와 그 안의 항목이 링크인 경우에 똑같이 적용한다.

- 있는지·디렉터리인지 묻거나 메타데이터·한 단계 목록을 요청할 때도 같은 검사를 거친다. 범위 밖 링크에는 "없다" 가 아니라 같은
  오류로 답하므로 루트 밖에 무엇이 있는지 드러나지 않는다.
- 읽기는 검사한 실제 경로를 연다.
- 조상으로 되돌아가는 링크는 경고와 함께 건너뛴다. 끊긴 링크는 일반 파일이 아니므로 목록에 없다.
- 허용 루트는 `PathSkillRepository.builder(root).allowedLinkRoot(...)` 로 정하고 기본값은 비어 있어 저장소 루트만 허용한다.
  디스크에서 읽는 에이전트 번들에는 설정으로 준다(스킬 가이드).
- 허용 루트는 절대 경로여야 하고 파일 시스템 루트일 수 없다. 상대 경로는 프로세스를 띄운 디렉터리에 따라 뜻이 달라지고, 루트는
  규칙을 끈다. 둘 다 목록을 받는 자리에서 거부한다. 없는 디렉터리나 루트로 가는 링크인 허용 루트는 아무것도 허용하지 않는다.

**읽지 못한 파일도 같다.** `.stageignore` 로 빼지 않은 항목을 스캔이 읽지 못하면 건너뛰지 않고 실패한다.

**실패의 범위.** `getAllSkills`, `reloadAll` 은 그 스킬을 경고와 함께 빼고 나머지를 돌려준다. 실패는 캐시하지 않으므로 이름으로
부르면(`getSkill`) 이유를 계속 말한다. 저장소 목록 자체의 실패와 파싱 오류는 그대로 전파된다.

**빈 사본 안전망.** 소스에서 `SKILL.md` 가 보이는 디렉터리가 파일 0개로 스캔되고 소스의 목록에도 파일이 없으면 레지스트리가
적재를 실패시킨다. 소스가 디렉터리 안을 보지 못한 것이다.

**머티리얼라이저와의 비대칭.** 스캔은 읽지 못한 파일에서 실패하고 머티리얼라이저는 건너뛴다. 그래서 같은 자원이 클래스패스
소스로는 거부되고 머티리얼라이즈 사본으로는 파일이 빠진 채 쓰일 수 있다. 허용 루트 아래의 링크 스킬이 머티리얼라이즈되지 않는 것은 [EE-82](../../backlog/execution-environment-open-items.md) 에 있다.

스윕은 반대로 링크를 전혀 따라가지 않는다(§13). 이 절의 규칙은 읽는 쪽의 것이다.

## 11. 제자리 지름길과 브랜치의 사본

자원의 소스가 워크스페이스 자체의 파일 시스템이고 규칙이 걸린 뷰에서 그 디렉터리가 **보이면**, 로컬 환경은 복사하지 않고 그
디렉터리를 돌려준다. 같은 인스턴스라는 것만으로는 부족하다. 제어 저장소처럼 숨긴 접두어 아래의 소스는 같은 인스턴스여도
복사한다. 제자리로 답한 경우 살아 있는 디렉터리를 받으므로 내용 키 검사와 상한을 거치지 않는다.

**격리 브랜치에게는 언제나 사본을 준다.** 제자리 경로는 부모의 작업 트리 안이다. 브랜치의 파일 도구는 그 경로를 브랜치 루트
아래로 옮겨 읽으므로 거기서 아무것도 찾지 못하거나 브랜치가 같은 이름으로 쓴 파일을 읽고, 브랜치의 셸은 같은 문자열로 부모의
파일을 연다. 두 쪽이 같은 파일을 보는 자리는 스테이징 영역뿐이다. 그래서 `LocalIsolatedEnvironment.stage` 는
`LocalStaging.stageCopy` 를 부른다.

- 사본은 **부모 트리의 스킬**이다. 브랜치가 자기 트리에서 같은 이름으로 고친 파일이 아니다.
- 적재된 판의 사본이 있으면 그것을 쓰고, 없는데 부모 트리에서 스킬이 바뀌었으면 §7 처럼 지금 내용의 키로 복사한다.
- 상한은 여기서 적용된다.
- 스테이징 영역은 환경의 작업 트리 밖에 있어 브랜치 병합에 사본이 섞이지 않는다. 브랜치가 그 접두어를 어떻게 공유하는지는
  [격리 브랜치](execution-environment-isolation.md) 에 있다.

## 12. `AIMON_SKILL_DIR` 본문 값과 포크 재렌더

이름은 같고 값은 둘이다. 합치면 값이 하나인 것처럼 읽힌다.

- **스킬 본문의 값**은 `stage()` 가 돌려준 스테이징 경로다. 이 문서가 소유한다.
- **스킬 훅 명령의 값**은 실행 디렉터리이고, 후퇴할 때만 스테이징 경로다. [훅 변조 경계](../hook/hook-tamper-boundary.md) 의
  호출자별 경로가 소유한다.

**포크 모드 스킬의 본문은 포크의 환경에서 다시 렌더한다.** 본문은 호출한 실행에서 렌더되므로 그 안의 `${AIMON_SKILL_DIR}` 는 호출한
쪽에 스테이징한 경로다. 제공자가 포크를 다른 환경에 두면 포크의 도구에는 그 경로가 없다. 렌더를 미룰 수 있는 자리는 포크의 환경이
있는 한 곳, `DefaultSubagentExecutor` 가 환경을 해석한 직후다.

- `SkillRenderContextAccess.rendersSkillDir(Skill)` 이 참일 때만 `Skill` 도구와 `LlmSkillExecutor` 가 `ForkGoalRenderer` 와 함께
  4인자 `SkillForkExecutor.fork` 를 부른다. 렌더러는 `SubagentLaunchContext` 를 거쳐 `SubagentExecutionRequest` 로 간다.
- 렌더러가 있고 포크의 환경이 부모와 다른 인스턴스일 때만 다시 렌더한다. 포크에 부모 인스턴스를 그대로 주는 로컬 제공자에서는
  다시 렌더하지도 다시 스테이징하지도 않는다.
- 다시 렌더하는 것은 스테이징 디렉터리뿐이다. 세션 id, 주체 같은 다른 렌더 값은 호출한 쪽의 것이다.
- `subagentStart` 의 goal 과 스팬 입력은 호출한 쪽의 글이다.
- 호출 쪽 스테이징은 포크 모드에서도 한다. 그래서 호출 쪽 스테이징이 실패하면 포크의 스테이징이 성공할 수 있어도 `Skill` 도구가
  실패한다.
- 4인자 `fork` 의 기본 구현은 3인자로 위임하므로, 재정의하지 않은 사용자 정의 포크 실행기는 다시 렌더하지 않는다.

포크에서 스테이징이나 렌더가 실패하면 포크는 `onStart` 전에 실패로 끝나고(`onStop` 없음, `subagentStop` 은 포크의 환경으로
발화) 메시지는 "Failed to render the fork's goal in its own environment: …" 다. "stage" 라고 쓰지 않는 것은 원인이 스테이징만이
아니기 때문이다. 사용 불가 환경으로 해석된 포크도 여기서 실패한다.

## 13. 스윕

로컬 제공자는 소유 워크스페이스 모드(`workspaceRoot`)에서만, 시작할 때, 이름마다 최신이 아니고 유예가 지난 사본과 마커 없는
디렉터리를 지운다. 링크를 따라가지 않고 실제 경로가 워크스페이스 밖이면 돌지 않으며, 내용 키 모양의 이름만 지운다.

- **유예.** 기본값은 24시간(`DEFAULT_STAGING_SWEEP_GRACE`)이다. 제공자의 `backgroundCommandTimeout` 이 더 길면 그 값으로 올라간다.
  사본은 그것을 읽을 수 있는 모든 명령보다 오래 살아야 한다. 소유 루트도 시작 때 조용하다는 보장은 없다. 같은 디렉터리의 다른
  프로세스, 축출 뒤 다시 만들어진 런타임의 백그라운드 명령이 옛 경로를 들고 있을 수 있다.
- **최신.** 이름마다 마커가 가장 새로운 사본은 유예와 상관없이 남긴다.
- **임시 디렉터리.** `{contentKey}.tmp-{32 hex}` 모양의 임시 디렉터리도 유예가 지나면 지운다.
- **링크.** 스테이징 디렉터리가 링크이거나 실제 경로가 워크스페이스 밖이거나 워크스페이스 자체이면 아무것도 하지 않는다. 이름과
  사본 수준에서도 실제 디렉터리만 내려가고 지운다.
- **이름.** 내용 키 모양(정확히 16자리 소문자 16진수)이 아닌 사본 디렉터리는 지우지 않는다. 잘못 설정한 스테이징 루트가 사용자의
  디렉터리를 지우지 못하게 하는 마지막 층이다.

빌린 파일 시스템(`.fileSystem(vfs)`) 모드에서는 돌지 않는다. 공급 VFS 배치에서는 사본을 원격 VFS 에 쓰므로 파일 도구는 읽지만
호스트 셸은 못 보고, 옛 사본과 임시 디렉터리는 스킬 버전 수만큼 쌓인다([EE-2](../../backlog/execution-environment-open-items.md)).

## 14. 입력 검증

스윕과 끊긴 복사의 정리는 이름을 믿는다. 그래서 잘못된 입력은 쓰거나 지우기 전에 거부한다. 손조립 `StagedResource` 가 밖에 쓰거나
정리가 제어 저장소를 지우지 못하게 하기 위해서다.

| 입력 | 거부 조건 | 시점과 오류 |
|---|---|---|
| 자원 이름 | 빈 값, `.`, `..`, `/` 또는 `\` 포함, `.gitignore` | `stage()`, `StagingException` |
| 내용 키 | 16자리 소문자 16진수가 아님 | `stage()`, `StagingException` |
| 기록된 파일 경로 | 상대 경로가 아니거나 빈 값, `.`, `..` 세그먼트, `\` 포함 | `stage()`, `StagingException` |
| 스테이징 루트 | 디렉터리 이름 하나가 아님(`.`, `..`, `/`, `\`, `:`), 제어 저장소 | 제공자 `build()`, `IllegalArgumentException` |

## 15. 실행 비트

VFS 복사는 POSIX 실행 비트를 남기지 않는다. 쓰기가 `VirtualFileSystem` 을 지나기 때문이고 머티리얼라이즈 사본도 같다. 그래서
`./x.sh` 로는 돌지 않고 스킬은 `bash`, `python3` 처럼 인터프리터로 부른다.

## 16. 실패 처리

| 상황 | 처리 |
|---|---|
| 복사가 중간에 끊김 | 마커가 없으므로 다음 `stage()` 가 다시 복사한다 |
| 상한 초과, 합쳐진 사본, 기록된 파일을 읽지 못함 | `StagingException`. 호출자(`Skill`, 스킬 기반 커맨드)가 도구 오류나 커맨드 오류로 바꾼다 |
| 사용 불가 환경 | `stage()` 가 던진다. 다른 스테이징 실패와 같은 길로 오류가 된다 |
| 저장소가 스킬을 찾았는데 소스가 없음 | 저장소 클래스 이름을 든 `SkillRepositoryException`. 그 스킬은 적재되지 않는다 |
| 적재 중 해시 I/O 오류, 범위 밖 링크, 읽지 못한 파일 | `SkillRepositoryException`. 그 스킬만 빠진다 |
| 클래스패스를 열거할 수 없음 | `SKILL.md` 만 보이는 소스와 WARN 하나 |
| 호스트 스킬 디렉터리가 읽기 전용이거나 없음 | 동작한다. 없는 루트에는 스킬이 없고 디렉터리를 만들지 않는다 |
| `StagedResource` 없는 손조립 `Skill`, 환경 없는 컨텍스트 | 변수는 비고 WARN 이 남는다. 저장소 경로를 쓰지 않는다 |
| 비영속 환경 재생성 | 대상에 마커가 없으므로 다시 복사한다 |
| 스테이징 실패한 스킬 훅 | 명령을 돌리지 않는다. 변수 없이 돌리면 다른 명령이 된다. 판정은 [fail-closed](../hook/hook-fail-closed.md) 의 경로별 동작 |

## 18. 하지 말 것

- **"이미 스테이징했다" 를 제공자 메모리로 판단하지 말 것.** 대상의 마커를 보고, 사본을 매 호출 내용 키에 대조한다(§4).
- **`${AIMON_SKILL_DIR}` 에 `stage()` 가 돌려주지 않은 경로를 넣지 말 것.** 저장소 경로로 되돌아가지 않는다(§9).
- **바이트를 그것이 해시되지 않는 키 아래 두지 말 것**(§7).
- **조립된 자원을 다시 스캔하지 말 것.** 목록에 없는 파일은 임시 디렉터리에도 쓰지 않는다(§7).
- **대상 디렉터리에 직접 복사하지 말 것**(§5).
- **매 호출 검증을 정책 훅의 근거로 삼지 말 것.** 확인 뒤의 창이 남는다(§4).
- **격리 브랜치에 제자리 경로를 주지 말 것**(§11).
- **스윕에서 링크를 따라가거나 내용 키 모양이 아닌 이름을 지우지 말 것**(§13).
- **빌린 파일 시스템의 스테이징 영역을 스윕하지 말 것**(§13).
